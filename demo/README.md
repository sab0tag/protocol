# Демо-стенд «Протоколу»

Вигадана «Демо-клініка» з тестовим входом і скиданням однією командою (ТЗ «демо клиники и тренировки», крок 1; D170). Живе на тому самому сервері, що й API Протоколу (рішення власника 18.11), окремим проєктом: своя база, свій `.env`, нічого з `protocol-api` не змонтовано, пам’ять кожного контейнера обмежена. Прод не зачіпається: там `CLINIC_IDENTITY_V2` вимкнений, клініка не створюється.

Адреси: `protocol-demo.<домен>` (застосунок), `api-protocol-demo.<домен>` (API), `idp-protocol-demo.<домен>` (тестовий вхід). Не `demo.<домен>` — на цьому сервері це демо Харчоблоку.

## Що тут працює

| Сервіс | Що робить | Назовні |
| --- | --- | --- |
| `web` | застосунок, зібраний для стенду (свій API, смуга «Демо · дані вигадані» на всіх екранах) | через спільний Caddy сервера: `protocol-demo.<домен>` |
| `api` | той самий сервер, що на проді, з `DEMO=1` і `CLINIC_IDENTITY_V2=on` | через спільний Caddy: `api-protocol-demo.<домен>` |
| `idp` | тестовий вхід OpenID Connect: адміністратор, ендокринолог, травматолог; другий крок — код `000000`, тож `amr` несе MFA, як вимагає D152 | через спільний Caddy: `idp-protocol-demo.<домен>` |
| `mailpit` | пастка для листів-запрошень: усе ловить, нікуди не пересилає; SMTP лише з STARTTLS і паролем | ні: вебінтерфейс на `127.0.0.1:8025` самого сервера |

## Замки

- Сервер з `DEMO=1` не стартує, якщо `APP_ORIGIN` не `protocol-demo.<домен>` (або localhost) чи вхід не через `idp-protocol-demo.<домен>`.
- Сервер без `DEMO=1` не стартує, якщо його `OIDC_ISSUER` вказує на `idp-protocol-demo.…`; а будь-який issuer, що в discovery називає себе демо (`x_protocol_demo_idp`), поза стендом нікого не впускає.
- Тестовий вхід не стартує без `DEMO=1` і поза `idp-protocol-demo.<домен>`.
- `demo:reset` відмовляє без `DEMO=1` (він є лише в `demo/compose.yml`).

## Розгорнути

1. DNS (власник): A-записи `protocol-demo`, `api-protocol-demo`, `idp-protocol-demo` → IP сервера.
2. На сервері: код у `~/protocol-demo` (rsync репозиторію без `node_modules`), потім `sh demo/setup.sh beyondthesignal.to` — створює `demo/.env` і `demo/.secrets/` (не в git), секретів не друкує.
3. Необов’язково: власний ключ ІІ для стенду в `demo/.env` (`ANTHROPIC_API_KEY`). Порожньо — фото, меню, помічник на стенді вимкнені.
4. `docker compose -f demo/compose.yml up -d --build`, потім `sh demo/reset.sh` (або `npm run demo:reset`, де є npm).
5. Три сайти з `demo/Caddyfile.shared` — у спільний `/opt/harch/deploy/Caddyfile`; `caddy validate`, потім `caddy reload` (ніколи не restart: той самий Caddy обслуговує Харчоблок і API Протоколу).
6. Перевірка: `https://api-protocol-demo.<домен>/health` → `"demo": true`.

## Скинути перед показом

`sh demo/reset.sh` (`npm run demo:reset`) — база з нуля, міграції, «Демо-клініка» з трьома працівниками; усі видані раніше коди зникають разом зі старою базою. API на час скидання зупинений.

## Пошта

`ssh -L 8025:127.0.0.1:8025 <сервер>` і відкрити `http://localhost:8025` — там листи-запрошення стенду.

## Що проговорити лікарю на показі

З `docs/clinic-secure-delivery.md`: для демо допустимо, для справжніх пацієнтів — ні: план зберігається відкритим текстом до погашення коду (ACCESS-07-B), ім’я лікаря приходить від клієнта (ACCESS-07-A).
